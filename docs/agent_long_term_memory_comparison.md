## 1. 结论摘要

三个项目解决问题的层次并不相同：

- **Mem0** 有直接可用的消息抽取、作用域内写入候选检索和普通记忆召回。历史动作式版本让 LLM 对候选做 ADD/UPDATE/DELETE/NONE；当前 `2.2.1` 自动推断写入则以 ADD 为主。当前普通召回比写入候选检索更丰富，但仍没有完整的事实时间线模型。
- **LangMem** 把记忆抽取/整理做成可组合 manager，把检索和存储放在 LangGraph `BaseStore` 一侧。Store Manager 能将有限候选交给模型，并通过 Trustcall 对已检索的结构化文档做 patch；但默认数据 schema 很薄，覆写不等于保留历史，时间、来源和冲突状态需要应用定义。
- **Graphiti** 将 episode、实体和关系事实组织成时序图。写入主路径结合旧 episode 上下文、实体消歧、事实候选混合检索、LLM 重复/矛盾识别和有效时间区间失效；保留旧边及其来源 episode。代价是更强的图数据模型和运行依赖，默认抽取也没有解决角色可信度、待核实冲突或当前态过滤。

阶段 3 曾提出较完整的组合候选：保留来源证据，以结构字段和混合检索找候选，由模型分类新旧关系，再执行历史变更。后续讨论已将首版收敛为公开搜索、原生新增/patch 和简单差异写回；首版不要求上述完整分类和编排。本文保留早期候选供比较，不声称它是最优实现。

阶段 3 当时只做了源码能力映射和方案草案，没有跑三套系统的对照实验或确定代码基座。后续组件探针和 2026-10-08 的复用方向另见阶段 4 与 v1 文档，不能把这段历史状态当成当前进度。

### 阶段 3 曾提出的最小版本（已由 v1 实施说明取代）

这份文档后面的字段和流程是**可评估的扩展设计**，不表示第一版都要实现。最小可用的长期记忆其实可以很简单：

1. 从对话里挑出值得以后记住的一条信息。
2. 存成一条记忆，并记录用户/项目范围和它来自哪条消息。
3. 写入前找几条同范围的相似旧记忆，避免重复；如果发现变化，明确保留旧值还是标记待确认。
4. 以后按当前问题找回相关记忆；问“现在”时不要把已被替代的旧值当成当前值。

第一版可以只有一张 `memory_item` 表；如果 DB-GPT 已保存原始对话，就存消息 ID/引用，不再复制一份对话。可先用这些字段：

| 字段 | 用途 |
|---|---|
| `id`、`scope_id` | 记忆编号，以及属于哪个用户/项目 |
| `type`、`content` | 信息类型（事实、偏好、计划、事件等）和记忆内容 |
| `source_refs` | 来源消息 ID；回答“为什么这么记”时回查原文 |
| `created_at` | 系统何时记下这条信息 |
| `observed_at` | 来源消息/事件何时发生；能从来源拿到时才填 |
| `valid_from`、`valid_to` | 可选：事实何时成立；不知道就留空 |
| `status`、`supersedes_id` | 当前有效、已替代或待确认；新旧条目之间的简单链接 |

写入时要区分几种情况：重复就不再造一条（可补来源）；**同一事实只是描述得更丰富时，可以直接更新原记忆并追加来源**；事实确实随时间变化时，再新增当前版本并把旧版本标为已替代；无法判断的矛盾才标待确认；无长期价值就不写。召回先限定用户/项目范围，再做现有向量检索。关键词混合、图关系、独立审计事件表和当前态缓存都可以等确有需要时再加。

时间字段也要分清：`created_at` 是系统存储时间，`observed_at` 是来源消息/事件的时间，`valid_from/to` 是事实实际生效区间。没有明确生效时间时，**不要默认把 `valid_from` 填成当前时间**；可以记录“这条信息在 `observed_at` 时已被确认”，但不能据此声称事实恰好从那一刻才开始成立。

首版的时间规则建议如下：

- 有原始消息时间戳时，用它作为 `observed_at`，也可作为解析“昨天”“去年六月”等表达的参考时间；导入旧对话时不能拿导入当天代替原消息时间。
- “从六月开始用 PostgreSQL”给出了变化时间，可以解析并填有效时间；“现在用 PostgreSQL”只说明在这条消息时间点观察到该状态，不说明它从这一天才开始。
- 没有明确起始/结束时间时，`valid_from/to` 留空。当前值仍可由最近一条明确、可信的当前状态记忆确定；更新旧值的“已替代”状态表示当前画像更新了，不等于知道现实中的精确切换时刻。
- 若用户先在时间 `T1` 说“现在我来上海了”，几天后在 `T2` 说“现在我回北京了”，保存两次带来源时间的当前位置报告；作为系统的“最近一次报告状态”，`T2` 后北京取代上海成为当前候选，上海仍保留为较早报告。若没说何时离开上海，不能断言切换恰好发生在 `T2`。问 `T1` 时回答“你在 `T1` 告诉我你当时在上海”；问 `T2` 时回答“你在 `T2` 告诉我你已回北京”。问“回北京之前在哪”时，可回答“此前最后一次记录是上海”，但不能声称那就是回北京前一刻的位置。问两者之间某一天的实际位置时，若无更多证据，应说明无法确定。

Graphiti 的抽取提示会用调用方传入的 episode `reference_time` 解释相对日期，并在当前状态时间不明时以 episode 时间作为 `valid_at`。这提供了一个实用的时间锚点，但也采用了更强的近似：在上面的例子里，可能把上海从 `T1`、北京从 `T2` 视为有效起点。自研首版可以借用可靠的 `reference_time`，同时把“观察到的时间”和“真实生效时间”分开；若以后为简化查询而用观察时间近似生效时间，应明确标注这是约定/估计。

所以，后文出现的 `SourceEpisode`、`Evidence` 等是为了把概念讲清楚，**不是要求首期建六张表**。最小版是“记忆条目 + 来源引用”；更完整的拆分要由隐私、追溯量和检索需求来证明其必要性。

## 3. 核心机制对照

| 维度 | Mem0 OSS | LangMem OSS | Graphiti Core |
|---|---|---|---|
| 记忆的基本对象 | 抽取后的文本记忆条目；另有辅助实体索引 | Store 中按 schema 保存的 JSON 文档；默认核心对象只有 `content` 文本 | 原始 episode、实体节点、实体间事实边；边连接来源 episode |
| 新输入 | 带角色消息或字符串；当前自动路径把整段新消息给模型，另取同作用域最近 10 条消息 | `messages` 列表整体进入管理器；调用方可传单条或多条、任意角色 | `add_episode` 接收文本 episode、source、group 和必传 `reference_time`；消息格式可把角色写进文本 |
| 写入前找旧记忆 | 历史版按每条抽取 fact 做向量 Top-5；当前版对整段新消息做作用域内向量 Top-10 | Store Manager 从 BaseStore 搜索，默认 Top-5；默认 query 由最近消息构造，也可用 `query_model` 生成 | 最近 episode 按时间/group/source 查询；实体按名称 embedding 去重；事实候选用 BM25+向量+RRF，重复和失效候选分开找 |
| 模型处理候选 | 历史版第二次 LLM 选 ADD/UPDATE/DELETE/NONE；当前版 LLM 只生成 ADD 候选，提示可返回链接 ID，但主路径不持久化这些记忆间链接 | Manager/Trustcall 在候选 JSON 文档上新增、patch 或按开关删除；具体决定由 prompt/schema 和模型完成 | LLM 把关系候选标成 duplicate/contradicted；随后代码根据新旧边的 `valid_at` 处理区间 |
| 更新历史 | 历史版 UPDATE 覆写旧向量文本并写 history；当前自动路径新旧并存。显式 API 与自动策略分开 | 更新复用 key 覆写值；LangMem 本身没有变更历史表或旧版本留存保证 | 正常冲突路径不删旧边，以 `invalid_at`/`expired_at` 表示事实有效区间与系统失效记录；episode provenance 保留 |
| 时间模型 | 主要有记录时间、可选过期字段；无默认事实 `valid_at`/`invalid_at` | Store `created_at`/`updated_at` 是记录时间；有效时间需自定义 schema/逻辑 | episode `reference_time`、边 `valid_at`/`invalid_at`、系统 `created_at`/`expired_at` 分开；未知事实时间允许为空 |
| 普通召回 | 当前版语义候选后融合 BM25/实体分数，可选 reranker；时间线过滤不足 | 走 BaseStore；实际检索由 Store 配置决定；无 LangMem 内建混合排序或时间线 | 默认边搜索 BM25+向量 RRF；高级接口支持图检索和显式时间 filter，但普通 `search()` 默认不筛当前有效边 |
| 对本项目有代表性的强项 | 接口直接、易用；写入和读取都有现成路径；历史版提供动作式冲突样本 | 抽取与存储解耦、schema 可定制、候选 patch 流程可组合 | 来源 episode、图关系、双时间及迟到历史事实处理形成一套较完整模型 |
| 关键默认缺口 | 当前自动写入不做语义更新/冲突判定；状态事实缺少时间和证据结构 | 默认 schema 太薄；检索漏召回会阻断更新；patch 覆写不保留状态历史 | 图模型不自然覆盖所有偏好/计划；候选有限，冲突 prompt 缺少结构化来源/时间，普通 search 不自动按当前时间过滤 |

### 3.1 写入候选检索不是普通召回

这是三个项目最容易混淆的一点：写入时检索是为抽取/去重/更新提供上下文，普通召回则是响应 agent 的用户查询。二者即使使用同一存储，也可能使用不同 query、数量、排序和过滤。

| 项目 | 写入候选 query 与检索 | 普通召回 | 重要区别 |
|---|---|---|---|
| Mem0 历史版 | 每条候选 fact 单独向量化，按作用域取 Top-5 | 独立 `search()` 路径 | 历史写入候选不是公开混合 search |
| Mem0 当前版 | 整段新消息向量化，按作用域取 Top-10；不跑 BM25/entity 融合 | 语义召回候选，再用 BM25 与实体分数重排，可选 rerank | 普通 search 的信号更丰富，但 BM25/entity 不会把语义候选集之外的记录重新召回；写入更新算法仍是 ADD-only |
| LangMem Store Manager | 默认从最近消息后缀构造 query；可用 `query_model` 生成多个 query；BaseStore 默认取 5 条 | BaseStore search 或 search tool，可由具体 Store 配 embedding/filter | LangMem 本身不保证底层是向量或混合检索；Store 决定实现。写入候选数量是 manager 的硬上下文边界 |
| Graphiti | 最近 episode 是时间查询；实体是名称相似检索；边是 BM25+fact 向量 RRF，另有限定同端点的重复候选 | 默认边搜索也是 BM25+向量 RRF；`search_()` 才能配置节点、episode、图遍历、reranker 和时间 filter | Graphiti 的“写入检索”有三种任务，不是一种向量查找；普通 `search()` 默认也不自动过滤失效时间 |

因此我们的候选流程应把用途分开：写入候选检索要围绕“同一用户/属性/实体的旧断言及可能矛盾”找证据；普通召回要围绕“用户这次问什么、问哪个时点、是否要来源”组织答案。写入检索漏掉旧事实会直接影响变更决策，需可观测并允许结构字段补召回。

### 3.2 更新和冲突判定不是“新文本覆盖旧文本”这么简单

| 项目 | 谁判语义关系 | 时间/来源是否是结构化判据 | 写回结果与风险 |
|---|---|---|---|
| Mem0 `v1.0.11` | LLM 根据提示词比较新 fact 与 Top-5 旧记忆，输出四种动作 | 没有有效时间、来源权威或置信度的结构化判据 | UPDATE 覆写旧文本，DELETE 删除活动向量记录；虽有 history，但当前值不再保留旧断言作为可查询时间线。候选漏召回或模型误判会导致错误动作 |
| Mem0 `2.2.1` | LLM 抽新记忆；精确重复由代码 hash 去重 | 无事实有效期；`created_at` 不是事实时间 | 自动路径不合并/更新/删除语义冲突旧条目；新旧可并存，但没有显式 contested/supersedes 状态 |
| LangMem Store Manager | Trustcall/LLM 对消息和候选文档做增量 JSON 操作 | 默认不是；可由自定义 schema、prompt 和应用补入时间/来源 | patch 后覆写同一 key；需额外版本表/事件来回溯。默认偏向整理一致，不保证冲突未决时 abstain |
| Graphiti 串行 `add_episode` | LLM 对检索候选的事实文本识别重复或矛盾 | 冲突 LLM 未收到候选边结构化时间/来源；之后代码才比较 `valid_at` | 时间可严格排序时更新旧边 `invalid_at`，旧边保留；未知或相同时间可能无法失效。不是新到达者无条件胜出 |

对我们的设计，**语义判定**应回答“同一事实、补充、演变、纠正、矛盾或无关”；**时间裁决**应回答“每条断言在什么时候成立”；**写回代码**应可预测地记录关系和区间。把三者塞进一次只看文本的 LLM 调用，难以审计、复现和回滚。

## 4. 按 S1–S14 的统一场景对照

以下判断针对各审查锚点的 OSS 默认路径；“可定制”不表示框架默认保障。Mem0 历史动作路径与当前路径分开写。

| 场景 | Mem0 | LangMem | Graphiti | 对自研设计的要求 |
|---|---|---|---|---|
| **S1 稳定偏好** | 当前可抽取，精确 hash 去重；改写重复依赖模型。历史版能对候选作语义动作 | 可用默认文本或自定义 schema 抽取并更新候选；默认无证据引用、无说话者强约束 | 可建成关系边并连 episode，但单体偏好不天然符合双实体关系 | 记忆类型应能表达用户偏好；同义重复可合并证据但不重复造状态；明确归属和来源 |
| **S2 个人事实** | 可抽取并按 scope 存储；来源 message/span 默认缺失 | 可抽取、可 patch；默认 schema 无来源/有效时间 | 关系图和 episode 可回溯到来源记录，但缺少精确证据跨度及可信角色规则 | 保存“谁的什么事实”，并能回指支持它的原始证据 |
| **S3 状态变化** | 历史版可能覆写；当前版只加新值，普通排序不保证当前值 | 检索到旧项后可 patch，但默认覆盖且无时间线 | 新旧事实矛盾且有效时间可比较时，旧边到新事实时点失效；保留旧边 | 新旧断言都保留；有时间依据时形成有效区间；当前态作为可重建投影，不以最新写入时间冒充事实时间 |
| **S4 明确纠正** | 历史版提示词可能 UPDATE/DELETE；当前自动路径不标记更正 | 可 patch，或显式开启删除，但更正关系/旧证据默认无独立记录 | 可因有效时间使旧边失效；没有固定 correction 事件和权威规则 | 区分“事实发生变化”和“此前陈述错误”；记下纠正者、证据及旧断言关系 |
| **S5 未确定计划** | 文本可保留“可能”，但默认无 intent/certainty 字段 | 自定义 schema 可建模计划状态/置信信息，默认只有 content | 可自定义边 schema；默认无计划/确定性类型 | 计划、意向、预测与已发生/当前事实分类型；计划取消不应抹掉现实状态 |
| **S6 未解决冲突** | 历史 LLM 动作可能武断覆写/删除；当前两条并存但无冲突标记 | 可在 prompt/schema 要求并存，但默认更偏整理，没强制待确认状态 | 图可并存两条带 episode 的边，但默认没有 pending-review 状态 | 支持 `contested/pending_confirmation`；证据不足时不自动选胜者，回答时表达冲突或澄清 |
| **S7 有参考时间的相对事件** | 历史无时间字段；当前 prompt 默认观察日期可能是处理当天，导入旧对话有误解析风险 | 文本日期可抽，但无专用 reference time 参数和默认双时间模型 | 调用方传 `reference_time`，抽取 prompt 可解析相对日期 | 输入 envelope 明确携带事件/对话时间和记录时间；相对日期只基于可信 reference time 解析 |
| **S8 原文无明确时间** | 无 valid-time 字段；系统创建时间不可当事实时间 | 自定义字段能留空，默认没有时间结构 | `reference_time` 必传；事实有效时间可为空，当前状态提示可能使用 episode 时间 | `valid_from/to` 可空并表达精度/不确定性；不得自动把 ingestion time 伪装成事件时间 |
| **S9 assistant 建议/推断** | 历史 user-scope 默认只抽用户消息；当前会抽 user/assistant 并标 `attributed_to` | 角色会进入 manager 输入，但默认不强制来源/归属规则 | 原始 episode 可保留 `assistant:` 文本，但没有信任级别 | 保存来源角色与断言归属分开；建议不可升级成用户事实，除非用户确认 |
| **S10 工具观察与用户确认** | 默认没有完整 tool-result/evidence contract | 可定制 schema，默认没有工具来源验证和确认关系 | episode source 可标来源并留原文，但缺少工具观察/用户确认结构化差异 | 分别建工具观察、执行事件和用户确认；保存执行目标/结果及确认指向，不保存隐藏思维链 |
| **S11 临时状态/过期** | 可设 `expiration_date`，但它是条目过期，不等于事实有效区间；旧版无自动语义到期 | Store TTL 取决 backend；不是事实 valid-time，也不自动结束语义状态 | 有结束证据或替代事实时可写 `invalid_at`，无默认 TTL/自动临时分类 | 区分保留期限和现实有效期；临时状态要么有明确 end time，要么召回时不升级为稳定画像 |
| **S12 当前、历史、来源查询** | 当前召回可融合词项/实体信号，但没有默认历史时点过滤；历史版更偏向语义搜索 | BaseStore query/filter 由存储实现；当前/历史/证据链需应用定义 | 边有双时间和 provenance；高级 filters 支持时间；普通 `search()` 不自动当前过滤 | 查询协议解析 `as_of`/时间段/来源意图；先做 scope、类型、时间约束，再排序并返回证据 |
| **S13 用户要求忘记** | 显式 delete 可删活动记忆，但 Mem0 history 留有文本；自动当前 add 不删 | manager 删除默认关闭；启用后 `adelete`，无统一跨副本删除审计/恢复策略 | 底层对象可删除，但自然语言遗忘不自动变成跨节点/episode 的策略 | 先定义忘记的对象、索引/副本/备份范围及法律保留；删除操作有授权、幂等和结果可核验 |
| **S14 用户/项目隔离** | 写入与读取按 user/agent/run ID filter | namespace template 可编码 user/team 范围 | `group_id` 限定图分区和候选 | 身份来自可信调用上下文；所有候选、写入、召回和删除都强制同一 scope，不能靠模型输出决定租户 |

## 5. 候选自研设计：分离证据、断言、当前态和变更

本节给出可供阶段 4 评估的设计草案。它不是最终数据库 schema；后续应结合保留策略和选择的存储验证。

### 5.1 对象边界

这些是**逻辑概念**，并非数据库表清单。第一版可以这样折叠：

| 逻辑概念 | MVP 怎么存 | 什么时候才值得拆开 |
|---|---|---|
| 来源记录 + 证据 | 如果已有对话表，只保存来源消息 ID；没有时可先保存一个来源引用 | 需要保留独立 episode、片段级引用、多种来源生命周期时 |
| 记忆断言 | `memory_item` 一行，保存类型、内容和 scope | 有强结构查询需求，或不同记忆类型字段差异明显时 |
| 证据关联 | `source_refs` 字段先保存一到多个来源 ID | 一条记忆经常由多条支持/反驳证据构成，需要分别审计时 |
| 变更历史 | 新旧记忆各留一行，用 `status` 和 `supersedes_id` 连起来 | 要记录复杂决策事件、操作人、回滚、审计和重放时，再加变更表 |
| 当前态投影 | 首期不建；从有效记忆记录中过滤 | 数据规模或查询延迟证明需要缓存时再加 |

完整设计仍可把来源 episode、证据片段、断言、证据关联、变更事件和当前态索引分开，但这是未来可能的拆分方案，不能据此推导“首期必须六个对象/表”。

### 5.2 扩展字段草案

下表是概念拆开之后可能需要的字段。MVP 优先使用本文件“先看最小版本”中的单表字段；只有使用场景要求时，才引入这些扩展字段或独立对象。

| 对象 | 扩展字段建议 | 设计原因 |
|---|---|---|
| SourceEpisode | `episode_id`, `scope_type`, `scope_id`, `source_kind`, `source_ref`, `occurred_at?`, `reference_time?`, `received_at`, `content_ref?`, `retention_policy`, `metadata` | 区分输入发生/参考时间与系统收到时间；原文保存可以按隐私策略配置 |
| Evidence | `evidence_id`, `episode_id`, `message_id?`, `speaker_role`, `source_kind`, `span?`, `confirmation_state`, `observed_at?` | 可回答来源、发言者及确认状态；避免 assistant/tool 结果误归属 |
| MemoryAssertion | `assertion_id`, scope, `memory_type`, `subject?`, `predicate?`, typed `value`/`content`, `modality`, `attribution`, `valid_from?`, `valid_to?`, `time_precision?`, `recorded_at`, `status`, `confidence?`, `dedupe_key?` | 结构化查询与文本语义召回并存；时间未知、计划和冲突都能表达 |
| 关系/变更 | `relation_type`（supports/contradicts/duplicates/refines/corrects/supersedes 等）, `source_assertion_id`, `target_assertion_id`, `evidence_ids`, `decided_at`, `decision_source`, `reason_code` | 把“事实关系”和“记录操作”说清楚，支持历史重建和审计 |

`confidence` 若使用，应带来源说明（模型估计、显式确认、规则判定），不能伪装成客观概率。有效时间采用可空区间和精度描述；日期只有年月或“夏天”时，不强造精确时间戳。

## 6. 候选写入与冲突处理流程

完整流程可以拆成很多阶段，但第一版可先收敛为五步：

```text
带角色的对话
  → 抽取值得记住的信息和来源消息 ID
  → 在相同用户/项目范围内找相似旧记忆
  → 判为重复、补充、明确变化、待确认冲突或不写
  → 保存记忆；变化时保留旧记录和新记录
```

**MVP 可以先复用现有向量搜索。** 结构字段、BM25/关键词并行检索、候选 trace、图检索、多级置信度、复杂事务/补偿和重建投影属于扩展项；先用场景案例证明需要，再决定增加。下面按较完整系统列出的细节是后续扩展参考。

首版的写入结果可按这张小表处理，不需要把每种情况都做成独立服务或复杂状态机：

| 输入与旧记忆的关系 | 简单处理 |
|---|---|
| 完全重复 | 不新建记忆；把新来源加到 `source_refs` |
| 同一事实更完整、彼此兼容 | `UPDATE` 原记忆内容并保留新旧来源；如需审计旧文本，再加版本历史 |
| 事实明确随时间变化 | 新增一条当前记忆，旧记录标记已替代；只有时间有依据时才填 `valid_to` / `valid_from` |
| 用户明确纠正之前说错的信息 | 更新当前记忆并保留纠正来源；需要查询纠错过程时再保留旧版本 |
| 两条话确实冲突、但对象/时间/来源不清 | 暂不覆盖，标记待确认；必要时向用户澄清 |
| 不值得长期记住 | 不写入 |

```text
可信调用上下文 + 带角色的输入 + 可用时间元数据
  → 保存/引用 SourceEpisode
  → 抽取候选断言与 Evidence 引用
  → 来源归属与记忆类型校验
  → 结构候选 + 关键词候选 + 向量候选（强制 scope filter）
  → 语义关系判定（可用规则与 LLM；需允许 abstain）
  → 时间/来源策略校验
  → 事务性写入断言、关系、变更事件和索引
  → 更新可重建的当前态投影
```

### 6.1 抽取与来源闸门

- 模型输出候选断言及其 evidence IDs/span；没有证据支持的推断不得作为确定事实写入。
- 明确区分用户陈述、assistant 建议、工具观察、外部文档和用户确认。assistant 说“可以用 Redis”不是用户决定；工具显示成功不是用户确认生产可用。
- `plan / preference / event / current state / past state` 等信息类型要显式保留。对不值得长期保存的闲聊允许不产出候选。
- 不保存隐藏 chain-of-thought；需要审计时保留结构化决策类别、证据引用和简要 reason code。

### 6.2 写入候选检索

- 先用可信 `scope_type/scope_id`、记忆类型、subject/predicate、实体 ID 等结构字段缩小范围。
- 在允许范围内并行找精确字段/同一属性候选、关键词/BM25 候选和向量语义候选；合并候选后去重和排序。重要属性可扩大召回或直接读取该属性的历史，而不是只信任 Top-5/Top-10。
- 将候选 ID、检索通道、分数和过滤条件写入 trace。检索无结果表示“本次没有找到”，不表示历史中绝对不存在冲突事实。
- 图关系搜索作为可选通道，用于实体关系/事件关联；不要求所有偏好和用户属性都必须变成图边。

### 6.3 语义动作与时间裁决分开

LLM 或分类器只从候选关系集合中选择并引用证据：

- `duplicate`：同一断言的重复表达，合并证据引用；
- `support/refine`：支持或增加限定信息；
- `supersede`：新状态接替旧状态，但只在属性/身份一致且顺序有依据时；
- `correct`：用户或权威来源明确说明旧信息错误；
- `contradict_pending`：相互矛盾且不能据现有来源/时间判定，保留并等待澄清；
- `coexist`：不同时间、主体、环境或计划/现实维度，不能硬合并；
- `unrelated / no_memory`：无关或不值得保存。

随后由确定性策略处理时间：只有事实有效时间有依据时才设置 `valid_from/to`。系统收到时间 `recorded_at` 永远不能自动替代事件发生/事实生效时间。新消息较晚不等于它描述的事实更晚（历史回填尤其如此）；来源权威、用户明确纠正、确认状态和谓词类型也要纳入策略。时间不明或同一时点冲突时保留待核实状态，不能默认“最新写入胜出”。

### 6.4 可审计写回

- 对一般状态演变，不静默覆写或物理删除旧断言；写入新断言、关系和变更事件，必要时结束旧断言有效区间。
- 对偏好/个人画像这类“当前摘要”，可以更新派生 current projection，但保留断言和证据版本供历史查询。
- 同一请求重试需幂等；断言、关系、变更事件与必要索引更新应有明确事务/补偿边界。
- 用户要求忘记不是普通 `supersede`：按策略停止检索并擦除受影响的原文、断言、embedding、图副本和缓存；审计中避免继续保存被要求忘记的内容本身。

## 7. 候选普通召回流程

1. 解析查询的 scope、实体/属性、记忆类型、时间意图（当前、`as_of`、历史区间）和来源意图。
2. 先应用可信 scope 与硬约束。对明确的“现在/去年/来源”问题，不能只靠语义相似度选 Top-k。
3. 组合精确字段/时间区间过滤、关键词检索、向量检索；实体关系问题再增加图遍历。各路候选可用 RRF 或学习/规则排序合并，随后可选 reranker。
4. “现在”问题读取最新的、明确且同一属性的状态报告；同时带上它的 `observed_at`。报告离当前时间较久时，回答“最近一次提到……”而不是无条件断言仍然如此。有效区间已知时，`as_of` 查询按区间筛选；区间未知时，只能回答“截至该时点最后一次报告的状态”，不能据此断言整个区间内持续成立。
5. “之前/变化前”问题要同时检索目标状态和它之前同一属性的记录，按 `observed_at` 排序。没有有效时间证据时，结果应表述为“此前最后一次记录是……”，不能升级成“紧挨变化发生前一定是……”。
6. 输出给 agent 的结果携带 assertion IDs、证据引用、来源归属、观察时间、可用的事实有效区间、冲突状态和不确定性；来源问题可继续取证据详情。
7. 检索到多个互相矛盾且不能裁定的候选时，返回冲突/不确定状态供 agent 澄清，不将排序第一条包装成已证实事实。

**设计原则：** 写入候选查找是“记忆整理的证据收集”；普通召回是“回答用户问题的上下文选择”。可以共用索引和检索组件，但查询意图、候选范围、时态过滤和结果契约应各自明确。

## 8. 取舍与未决点

| 决策问题 | 当前草案 | 仍需结合产品/阶段 4 决定 |
|---|---|---|
| 原文证据保留 | 记忆应有稳定 source/message 引用；原文完整留存可配置 | 保存完整对话、片段还是只保留引用？加密、TTL、用户删除和审计保留边界是什么？ |
| 冲突默认动作 | 不足以裁决时保留 `contradict_pending`，不自动覆盖 | 是否对高置信、明确纠正开放自动替代？哪些谓词允许自动处理？ |
| 时间缺失 | `valid_from/to` 可空；保留 reference/record 时间及精度 | 当前陈述何时可以用 episode 时间作为 valid_from？哪些来源时间可信？ |
| 当前态建模 | 原始断言/变更事件是事实源；projection 可重建 | 使用关系表、版本表、图边，还是混合存储？ |
| 跨 scope 共享 | scope 必须硬过滤；暂按 user/project 两级建模 | 个人、项目、组织共享的权限与继承规则是否属于首期？ |
| 遗忘 | 与事实更新分开，要求覆盖所有可检索副本 | 物理删除、审计、备份和依法保留的具体策略？ |
| 记忆种类 | 初期支持事实、偏好、状态、事件、计划、工作事件 | 未确认的 agent 工作结果能否长期保存、保存多久？ |
| 候选成本/完整度 | 结构+关键词+向量分路，重要属性可扩召回 | 召回数量、embedding/LLM 次数、延迟及后端成本需原型测量 |

## 9. 阶段 4 基座评估结果

阶段 4 不应只问哪个 repo “功能最多”，而应拿本方案的数据契约和流程，对照三种路线：

1. **基于 Mem0 改造：** 评估如何接入证据/时间/变更关系，以及是否保留其作用域、抽取和检索组件；不能把当前 ADD-only 默认能力误当成冲突管理。
2. **基于 LangMem 改造：** 评估 schema/manager/Store adapter 可复用度，以及补造版本历史、证据模型、时间决策和统一数据 envelope 的工作量。
3. **基于 Graphiti 改造或复用图层：** 评估 episode/provenance/时态边可复用度，及图数据库、运行依赖、偏好/计划建模、角色信任和普通查询时间过滤的差距。
4. **独立核心 + 复用存储/检索组件：** 评估是否将冲突和记忆契约掌握在 DB-GPT 适配之外，同时比较自己维护写入策略的成本。

评分应基于目标场景覆盖、历史/纠错语义、证据追溯、检索可控性、scope 安全、依赖和许可证、与选定后端的契合度、升级维护及原型验证。固定版本的路线评估和候选建议已形成，见[阶段 4 评估](agent_long_term_memory_phase4_evaluation.md)；建议仍待原型验证。
