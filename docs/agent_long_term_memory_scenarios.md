# Agent 长期记忆：首期场景与验收标准

> 状态：工作草案 v0.1。本文定义首期记忆系统需要解决的问题，已用于 Mem0、LangMem、Graphiti 源码审查和统一设计对照；它不预设采用哪一种实现或存储架构。
>
> 使用方式：S1–S14 是设计检查和评估用例，不是 14 项都必须单独开发的功能。首期核心、条件性边界测试和暂缓范围见 [v1 设计草案](agent_long_term_memory_v1_design.md)；对照表中的“期望处理”用于检验结果，不要求照搬成字段、状态机或独立子系统。

2026-10-08 交接审核：本文是检查问题的素材，首版字段、实现范围及任务顺序以 [v1 设计与实施说明](agent_long_term_memory_v1_design.md)为准。表中的“标记待确认”“过期后不作为当前常态”“按问题时间范围选择”等期望，可以先由记忆文本、来源/时间与回答模型表达；不要求新增 pending 状态、自动过期任务或查询分类器，也不要求在代码实现前准备完整评测。

## 1. 目标与边界

首期目标是让 agent 在后续对话中能使用**有来源、可更新、可追溯**的持久信息，重点是用户明确表达的事实和偏好、状态变化及重要事件。Agent 工作结果是可选范围，不把 DB-GPT 的执行日志记忆自动当作首期长期记忆目标。

记忆系统需要从对话及其元数据中筛选值得保留的内容，判断新内容与已有记忆的关系，并在未来问题中召回适当的信息。系统不能把每条对话、assistant 推理过程或未经确认的模型输出都当成用户事实。

### 工作假设

- 首期以跨会话的用户相关记忆为主；用户、项目或组织的记忆范围必须隔离。项目级或组织级共享记忆是否属于首期范围，仍待确认。
- 每条记忆应能追溯到其来源；至少保留来源类型及原始对话/文档/事件的引用。
- “事实何时成立”与“系统何时获知”是不同时间。事实时间可以未知；系统不得为了填满字段而编造时间。
- 原始对话/事件证据与从证据中整理出的记忆是两种不同对象。是否长期保存完整原文，留待隐私、成本和审计需求确定。
- 记忆策略先按用户可见的预期结果评估；ADD、UPDATE、DELETE 等框架动作名不作为需求本身。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 来源记录 / episode | 一段对话、文档或事件及其角色、时间和来源信息，用来证明记忆从何而来。 |
| 候选记忆 | 从来源记录中提炼、尚待判断是否写入的事实、偏好、状态或事件。 |
| 当前状态 | 对某项会变化信息，系统根据已有证据判断在指定时点成立的值。 |
| 有效时间 | 事实在现实中成立的时间或时间区间；不确定时可以留空或标为不确定。 |
| 记录时间 | 系统接收或保存来源记录、记忆的时间。 |
| 记忆变更 | 新内容导致新增、合并、补充、替代、并存待核实或删除等语义结果；具体实现动作由设计阶段决定。 |

## 3. 首期场景矩阵

| ID | 场景与输入示例 | 期望保留的信息 | 已有记忆的预期处理 | 后续召回验收 | 不可接受的错误 |
|---|---|---|---|---|---|
| S1 | **明确的稳定偏好**：用户说“我喜欢简洁的回答，代码示例用 Python”。 | 两项可用于个性化回答的偏好；保留用户及消息来源。 | 首次建立；同义重述应补充证据或保持一条逻辑记忆。 | 后续解释问题时遵循偏好；询问偏好来源时能指向用户陈述。 | 把偏好扩写成用户没有表达的属性；为每次重复生成一条重复记录。 |
| S2 | **明确的个人事实**：用户说“我在 Acme 做数据工程”。 | 用户陈述的职业/组织事实及来源。 | 同一事实重复出现时去重，保留多个证据引用或可信度信息。 | 问“我在哪里工作？”时返回该信息并能说明来源。 | 将 assistant 猜测、上下文暗示写成用户确认事实。 |
| S3 | **状态发生变化**：旧记忆为“使用 MySQL”；用户后来说明“从六月起项目迁到 PostgreSQL”。 | 新状态及迁移时间；旧状态作为历史保留。 | 在证据足够时标记旧状态的有效期结束，并记录新状态的开始；不要物理抹掉历史证据。 | “现在用什么？”返回 PostgreSQL；“六月前用什么？”返回 MySQL。 | 永远只保留旧值；把历史值当成当前值；没有依据就推断确切日期。 |
| S4 | **明确纠正**：用户说“我之前说住在北京是错的，我一直住在杭州”。 | 更正后的事实及其明确纠正关系。 | 旧错误记忆被更正/标注为错误，同时保留可审计的来源和变更记录。 | 当前问题返回杭州；审计问题可说明曾更正。 | 把旧错误继续作为当前事实召回；静默删除导致无法解释变化。 |
| S5 | **尚未确定的计划**：用户说“我可能明年搬去上海”，之后又说“还没决定”。 | 计划及其不确定状态；不等同于已搬迁的居住事实。 | 更新计划状态或补充不确定性，不替换当前居住地。 | “你现在住在哪里？”不得仅据此回答上海；“考虑过什么计划？”可召回上海计划。 | 把意向写成已发生事件或确定状态。 |
| S6 | **来源冲突、无法判定**：对话中两个时间相近的用户陈述互相矛盾，且没有明确纠正或先后解释。 | 两条带来源的证据和冲突状态；必要时等待澄清。 | 暂不武断地覆盖其中一条；可标注待核实。 | 回答时指出不确定或询问澄清；不能把猜测包装成确定事实。 | 仅因向量相似或某条记录较新，就无条件判定新陈述正确。 |
| S7 | **带相对时间的事件**：有可信对话时间戳时，用户说“去年五月加入这个项目”。 | 事件及可解析的时间；保存用于解析的参考时间/来源。 | 将事件时间与系统记录时间分别保存。 | 查询事件发生时间时给出正确年份，必要时说明其依据。 | 没有参考时间仍自行确定“去年”的年份；把记录日期误当事件日期。 |
| S8 | **没有明确时间**：用户只说“我现在负责支付服务”，输入没有可靠时间戳。 | 当前职责陈述、来源和记录时间；事实有效时间未知或仅能标记为“陈述时的当前状态”。 | 后续有充分证据时可更新；在时间未知时避免制造精确时间区间。 | 询问来源时能找到陈述；时间相关回答准确表达信息边界。 | 把系统处理时间伪装为事实开始时间；凭空写入 `valid_at`。 |
| S9 | **assistant 建议或推断**：assistant 建议“可以用 Redis”，用户没有确认。 | 作为对话事件可保留（若有必要），不能成为用户已采用 Redis 的事实。 | 不覆盖用户技术栈、偏好或项目状态。 | 问“我决定用什么数据库？”时不得把 assistant 建议说成用户决定。 | 将 assistant 输出、模型推测自动归属为用户事实。 |
| S10 | **工具结果与用户确认的执行结果**：工具显示部署成功，随后用户确认“生产环境验证通过”。 | 区分工具观察和用户确认；可保存成带来源的 agent 工作事件。 | 确认补充证据，但不把整个工具日志或 agent 思维链升级为个人事实。 | 问“上次部署结果如何？”能返回已确认结果及来源。 | 把未验证的工具输出当作用户确认；保存隐藏推理过程作为长期记忆。 |
| S11 | **临时信息与过期状态**：用户说“这周住在东京出差”，之后行程结束。 | 有期限的事件/临时状态及来源。 | 过期后不再作为当前常态召回；历史查询仍可找到。 | “我现在在哪？”不应返回已经结束的临时行程；问上周行程可正确返回。 | 将临时事实长期当成稳定个人资料。 |
| S12 | **当前值与历史值检索**：已有多个带时间、来源的同一属性记忆；用户分别问“现在是什么？”、“去年是什么？”、“依据是什么？”。 | 对应时段的状态及证据链。 | 读取时按问题时间范围选择，不只挑语义最相似的条目。 | 当前、历史和来源查询分别返回正确结果。 | 把写入时找相似旧记忆和普通问答召回混为一谈；返回无来源的结论。 |
| S13 | **用户要求删除或忘记**：用户要求忘记某项个人信息。 | 记录并执行用户的删除意图；删除范围和审计策略遵循明确的产品规则。 | 相关记忆不再参与正常召回；底层证据、备份和审计记录如何处理需有一致策略。 | 后续普通查询不再泄露该信息；系统可按产品规则说明处理状态。 | 只删除向量索引但保留可被其他路径召回的副本；删除范围不一致。 |
| S14 | **用户/项目隔离**：不同用户或不同项目分别保存相似事实。 | 记忆始终归属正确的用户/项目命名空间。 | 更新、去重、冲突判断仅发生在允许的作用域内。 | 一方的查询不会返回另一方私有记忆。 | 跨用户、跨租户或跨项目泄露；在错误作用域内合并记录。 |

## 4. 统一验收维度

后续每个候选项目及原型都应使用同一批场景，至少评估：

1. **抽取正确性：** 值得记住的信息是否被提取；普通闲聊、助手建议和未确认推断是否被过滤或正确标注。
2. **来源归属：** 记忆能否回到说话者、来源记录和证据片段；用户陈述、assistant 输出、工具结果是否区分。
3. **变更正确性：** 对重复、补充、更正、状态变化和未解决冲突，是否得到预期语义结果并保留历史。
4. **时间正确性：** 事件时间与记录时间是否区分；相对时间是否有可靠参考；不确定时间是否保持不确定。
5. **召回正确性：** 当前状态、历史状态和来源查询能否区分；无关记忆是否被排除。
6. **隔离与删除：** 作用域过滤是否有效；删除意图是否能覆盖实际召回路径。
7. **安全失败：** 输入不足或证据冲突时，系统能否选择不写入、标为待确认或表达不确定，而非编造确定结论。

首轮对比应报告每个场景的成功/失败和具体错误案例。后续有标注数据后，再汇总精确率、召回率、冲突决策准确率、时间解释准确率、来源归属准确率、检索命中率、跨域泄漏次数、时延和模型调用成本。任何汇总分数都不能掩盖将未确认信息写成事实或跨用户泄漏等严重失败。

## 5. 后续逐例记录格式

每个评测用例应至少包含：

```yaml
case_id: S3
scope: user-123
reference_time: 2026-09-28T10:00:00+08:00
input_messages:
  - role: user
    content: "从六月起项目迁到 PostgreSQL。"
expected_candidate_memories: []
expected_state_transition: "旧状态保留为历史，新状态成为有时间依据的当前状态"
expected_time_interpretation: "记录事实时间与系统记录时间；只有依据足够才解析具体年份"
recall_queries: []
must_not: []
```

具体字段可以随候选系统的接口调整；用例表达的预期语义应保持一致。

## 6. 早期产品问题的当前处理

这些问题在初期被列为待讨论项；首版已有推进约定，不应在交接时再次作为必须先询问用户的阻碍：

| 问题 | 当前首版处理 | 后续边界 |
|---|---|---|
| 个人还是项目记忆 | 单次操作由程序指定 user 或 project scope，分别隔离。 | 组织权限和自动跨范围合并后置。 |
| 未确认的执行结果 | 有复用价值时可按工具/assistant 来源保留，不能当用户确认。 | 保存期限和完整工作事件产品范围后置。 |
| 原始对话保存 | 复用来源 ID/角色/时间；核心不复制完整聊天原文。 | 原文读取与保留取决于调用方聊天存储，生成 ID 不自动保证原文存在。 |
| 遗忘范围 | 首版按明确记忆 ID 删除，退出普通记忆召回。 | history、聊天、备份及派生内容全范围删除属于生产策略。 |
| 无法解决的矛盾 | 保存有来源的内容，回答时说明不确定或澄清。 | 不建立人工审核队列，不自动推断胜者。 |

## 7. 阶段 1 结论与使用情况

首期记忆场景已形成可用于源码审查的基线：稳定信息、状态演变、明确纠正、未解冲突、时间缺失/解析、assistant 与工具来源区分、事件回忆、过期、删除和隔离。

本表已用于 Mem0、LangMem、Graphiti 的固定版本源码审查及三方统一对照。统一映射和初步设计取舍见 [Mem0、LangMem、Graphiti 统一对照与自研设计草案](agent_long_term_memory_comparison.md)。若后续源码复核或原型评估暴露新的必要场景，再回到本文补充；不因某一候选项目默认支持某项能力就直接把它提升为需求。
