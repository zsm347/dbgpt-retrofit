# Agent 长期记忆原型：先测组件，再测完整链路

> 状态：阶段 A 组件与组合接线已观察；阶段 B 已开始多类型小样本观察，并完成一轮失败修正和复跑；阶段 C 的任务收益对照尚未实施。  
> 目的：避免把完整记忆系统的验收问题误当成“最小原型”现在就能回答的问题。

2026-10-09 进度说明：阶段 A 是此前组件探针和两批组合代码的接线观察。随后已运行六组多类型样本、审阅形成的记忆与回答，并修正其中的工程协调和部分提取问题。最新结果见本文末节；仍存在语义失败，尚未通过整体记忆质量验收。当前编码以 [v1 实施说明 16、17，尤其 17.8](agent_long_term_memory_v1_design.md)及实际代码为准。

## 先澄清：上海例子能测什么

“我现在在上海” → “我回北京了”适合作为**写入流程演示**。若预先给系统一条上海记忆，可以观察 LangMem 会不会提出更新、Mem0 会不会新增北京记忆，以及它们各自返回什么。

但在还没有自有历史写回、问答检索和回答层时，它不能回答“当前问题是否选对北京”“历史问题是否找回上海”。这些属于完整链路行为。上一版把演示用例、组件测试和系统验收混在了一张清单里，范围不对。

## 阶段 A：最小组件原型现在能测什么

这个阶段只回答“组件接不接得上、默认行为是什么、要补哪些接口”，不评价长期记忆系统的整体正确率。

| 小用例 | 做法 | 当前能观察什么 | 不能据此声称什么 |
|---|---|---|---|
| A1 新信息 | 给一段带角色的对话，不提供旧记忆。 | API 是否能接收消息；会输出什么候选；调用需要哪些模型/存储依赖。 | 不证明长期记忆提取准确。 |
| A2 重复/补充 | 准备一条旧记忆，再给重复表达或补充信息。LangMem 显式传入 `existing`；Mem0 先预置同一条记忆，再运行 `add()`，记录其实际找到的候选。 | LangMem 如何输出既有条目的更新/保留结果；Mem0 写入时是否找到旧候选、最终新增什么。 | 若两边实际看到的旧候选不同，不能把结果差异单独归因于模型的提取能力。 |
| A3 冲突/状态变化 | 预置“用户说现在在上海”，再输入“我回北京了”。 | 两条 API 路径各自返回什么；旧记录是否被框架原地改写、留下或新增。 | 不评价历史能否保留，也不评价用户问“现在/之前”时是否回答正确。 |

原型逐步记录实际输入、实际旧记忆候选、模型返回值、写入结果、依赖和调用边界。LangMem 无状态 manager 的旧候选由调用程序提供；Mem0 `add()` 有自己的候选检索路径。若候选不同，这一轮只能比较两条**实际集成路径**，不能声称是在相同检索结果下单独比较提取器。[LangMem manager 源码](https://github.com/langchain-ai/langmem/blob/56d85939d80bb731bd5e237567148d817d7bfd16/src/langmem/knowledge/extraction.py)；[Mem0 add 源码](https://github.com/mem0ai/mem0/blob/94c3fe9f238f3dbf29c9ce98643bd71eb13077cd/mem0/memory/main.py)

阶段 A **不实现**自定义来源/事实时间契约、历史版本写回、新旧关系、通用当前/历史查询、遗忘级联或完整回答流程。A1–A3 是接口和行为探针，不是有统计意义的准确率评测。

### 已完成的小规模探针（2026-09-29）

使用临时独立环境安装 `langmem==0.0.30` 和 `mem0ai==2.2.1`，没有克隆源码，也没有改 DB-GPT 的依赖或配置。两边都通过本机已有的 Qwen `qwen-plus` 配置处理合成中文消息；Mem0 使用该配置的 `text-embedding-v3`，向量数据写入临时 Qdrant 目录。新信息各跑一次；重复表达、信息补充和状态变化各用两种说法跑过。样本仍很小，结果仅用于了解接口行为。

| 探针 | LangMem 无状态 manager 的实际返回 | Mem0 `add()` / `search()` 的实际返回 |
|---|---|---|
| 新信息 | 对“我偏好回答简洁一些”返回一条偏好记忆，但补充了“所有未来回答”等概括和 `p=0.99`。 | 对“我平时喜欢答案先给结论，再简要解释”新增一条偏好记忆。 |
| 重复表达 | 两种说法下都返回原 ID 的旧条目，并另给一条新 ID 的概括记忆；本次没有把内容合并进原 ID。 | 两种说法下都检索到旧偏好，`add()` 都返回空结果，存储仍只有旧条目。 |
| 信息补充 | 给“在数据平台组负责数据质量”补充“主要负责 ETL 监控”后，返回了修改过的原 ID，也另返回一条新 ID 的概括记忆。 | 检索到旧条目后新增了 ETL 监控记忆，旧记忆仍保留；没有合并成单条记录。 |
| 状态变化 | 给上海旧记忆和“我回北京了”后，一次只返回同 ID 的更新版本；换一种表述后，同时返回同 ID 的更新版本和一条新 ID 的概括。两者都是 manager 输出，尚未写入持久存储。 | 两种说法下都检索到上海旧记忆并新增北京记忆；两次新文本都加入原文没有提供的“around September 29, 2026”。一次对历史问法调用 `search()` 时两条记录都进入结果，但没有接回答模型，所以没测出历史问答是否正确。 |

这些是**少量、特定模型配置下的观察**，不能据此断言总体准确率或稳定性。当前值得后续处理的点是：LangMem manager 可能同时返回更新项和新概括项；Mem0 本次重复输入没有新增，但补充/状态变化会另加一条。两次位置变化输入都含“现在”，输出把状态变化落在约 2026 年 9 月 29 日；这个日期可由探针的观察日期解释为近似的消息时间参照，不代表系统知道用户实际迁移的精确日期。它说明需要区分消息观察时间与事实发生时间，不证明所有模型或输入都会如此。

此次临时探针还验证了一个适配细节：本机 DB-GPT embedding 配置给出的是完整 embedding URL，而 Mem0 的 OpenAI 兼容客户端需要基础 URL；临时探针做了路径适配，没有更改用户配置。临时 Python 环境位于 `/tmp/dbgpt-memory-probe-langmem` 和 `/tmp/dbgpt-memory-probe-mem0`。

### 第一轮真实组合链路观察（2026-10-09）

本轮没有改 DB-GPT 主依赖或用户配置。使用 `~/.dbgpt/configs/qwen.toml` 中的 Qwen OpenAI-compatible 配置，在独立临时目录创建 Mem0 2.2.1 本地 Qdrant collection，调用当前 `MemoryService`、LangMem 0.0.30 manager 和 `text-embedding-v3`。API key 只在进程内读取，未写入代码或输出。运行环境没有安装 spaCy 和 fastembed，所以本轮实际是向量检索路径；Mem0 的可选实体/BM25 信号没有参与。

真实运行观察到：

1. 初次偏好会 ADD；重复表达被 manager 返回为同一条对象并合并新的来源 ID，程序 UPDATE 原 Mem0 ID，没有堆出第二条重复偏好。
2. 补充偏好时，manager 返回了一条更具体的新偏好和一条未改变的旧对象；程序 ADD 新对象并 SKIP 旧对象，说明写回层的对象比较能挡住未改变返回值，但不能保证模型不会产生新的概括条目。
3. 对数据库状态变化，模型新建 PostgreSQL 对象，并提出替代旧 SQLite 对象；程序先 ADD 新对象，再给旧对象写 `superseded_by`。有明确切换日期的输入中，旧 `valid_to` 和新 `valid_from` 被正确保留。
4. 没有明确事实日期、只有“我现在在上海”→“我现在回北京了”时，模型仍把两条来源的 `observed_at` 写成了 `valid_from`/旧 `valid_to`。这违反本原型“消息观察时间不自动成为事实有效时间”的提示约定；当前程序只做非空和顺序检查，因此没有拦截。这是实际模型行为风险，不是 fake/stub 能发现的。
5. 同一位置变化的第一次输出还暴露了来源归属问题：关系 patch 原先会把“回北京”消息并入旧“在上海”记录。该消息支持新状态和可能的切换边界，不应重新证明旧正文；代码已改为旧记录保留原 `source_refs`，新来源只写入新记录。
6. `search()` 返回了当前北京和已被替代的上海两条记录；在另一组数据库查询中，旧 SQLite 记录还曾排在新 PostgreSQL 记录前面。向量相似度不会自动理解 `superseded_by` 或“当前/历史”意图，回答侧必须读取替代标记、来源和可用时间后再组织答案。当前原型没有偷偷做“全局只保留最新”过滤。

这轮运行证明的是组合链路可以真实调用、写回和返回 metadata，不是记忆质量达标。它暴露出两个需要用下一轮设计/实验解决的具体问题：

- **事实时间来源校验：** 仅靠 instructions 不足以阻止模型把 `observed_at` 当 `valid_from`。下一步要在不误伤明确日期、相对日期和未知日期的前提下，决定采用结构化时间依据字段、窄规则校验，还是先记录告警再扩大样本；在决定前不把消息时间自动改成事实时间。
- **回答侧结果组织：** 普通向量搜索可以同时返回新旧记录，甚至排序相反。下一步要用多种任务观察回答模型是否能正确利用 metadata，再决定是否增加轻量的查询意图/时间过滤；当前不把一个位置例子当作整体验收。

本轮使用的临时目录均在系统临时目录中，未写入仓库数据目录；运行日志中的可复现信息是配置版本、依赖版本、collection 和观察结论，不保存密钥。

### 时间提示收紧后的定向复跑（2026-10-09）

为区分“现在”本身和“状态替代上下文”的影响，随后用同一真实配置做了四个独立输入：

- “我现在住在上海。”：`valid_from`/`valid_to` 均为 `null`，来源 `observed_at` 单独保存；
- “我从 2026 年 10 月 1 日起使用 PostgreSQL。”：保留 `valid_from=2026-10-01`；
- “我计划下个月搬到深圳。”：模型按消息观察日期换算为 2026 年 11 月的计划区间，并保留“计划”措辞；
- 普通偏好：没有事实时间字段。

随后把提示明确收紧为“现在/目前/当前”只表示在消息观察时看到该状态，不自动生成开始/结束时间，再复跑“现在在上海”→“现在回北京了”。两条记录都保留 `valid_from`/`valid_to=null`，替代关系仍然写入，且旧上海记录只保留原 `loc-1` 来源，新北京记录使用 `loc-2` 来源。这个结果支持当前的简化约定：消息时间始终记录在 `observed_at`；“现在”没有足够依据时不填事实区间；明确日期或可由可靠观察时间换算的相对日期才允许填写。它仍是定向样本，不能证明提示词对所有输入稳定有效，因此暂不把 schema 扩展成更复杂的时间类型，也不把程序校验宣传为已经解决时间推理。

### 回答侧带参考时刻的定向复跑（2026-10-09）

随后用过去的消息时间重新写入位置和数据库状态，并在回答上下文中显式加入程序提供的 `reference_time=2026-10-09T08:00:00Z`。候选仍由同一个 Mem0 `search()` 返回，包含正文、来源、`observed_at`、事实时间和 `superseded_by`，没有在搜索层预先删除旧记录。

在这组输入中，回答模型能够：

- 当前问题选择未被替代、且在 `reference_time` 已生效的记录；
- 历史问题读取被 `superseded_by` 指向的旧记录；
- 使用来源的 `observed_at` 解释报告先后，不把 `recorded_at` 当成事实发生时间。

前一轮没有显式 `reference_time`，且测试消息时间被故意设在系统当前日期之后，模型会花篇幅解释“未来时间”并按最新未替代记录回答。这个现象说明回答上下文需要一个由程序提供的参考时刻；它不说明搜索层必须全局过滤旧记录。当前最小契约是：`search()` 返回有限候选和完整 metadata，回答调用同时收到 `reference_time`，由回答模型结合问题意图使用；是否再加轻量时间过滤要由更多任务失败决定。

随后将该契约收敛为 `memory_v1.answer.build_answer_context()` / `build_answer_prompt()`，要求调用方显式提供带时区的 `reference_time`，并保持候选原顺序、不在辅助层过滤旧记录。真实回答模型直接消费新 prompt 的 smoke 已正确选择未被替代的北京记录；这只是接线验证，不是回答质量评测。

**2026-10-08 交接审核的证据边界：** 上述两个临时环境目前均已不存在；当前仓库也没有随文档保存探针运行脚本、完整原始响应及当时的传递依赖锁文件。因此这部分是此前运行的文字记录，无法仅凭仓库完整复现当时输出；源码行为仍可按固定提交独立复核。不得把文字观察升级为本轮重跑确认、组合兼容性证明或质量排名。交接后的第一版实现应保存自身依赖锁文件、运行命令和实际结果；不以恢复旧临时目录为前置任务。

## 阶段 B：评估记忆质量和整理是否合适

阶段 B 不是只做“现在/之前”的问答。先实现最小的自有记忆记录与写入层，然后检查系统形成的记忆是否符合预期：

- 有用且有依据的信息是否被记住；无依据的推断是否被当成事实。
- 重复信息是否造成冗余；补充信息是否被合理吸收；真实变化和明确更正是否被错误合并或覆盖。
- 用户陈述、assistant 建议和工具观察是否保持正确归属；消息时间与事实时间是否混淆。
- 计划、暂时状态和稳定偏好是否被整理成适合后续使用的内容，而非丢失原有语气或上下文。
- 相关记忆是否能在不同类型的后续任务中被找到；检索是否漏掉关键内容或引入不相关旧信息。

这里要检查实际保存的记录和实际召回的证据。历史问答可以包含在用例中，但只是“记忆是否可用于某类任务”的一个例子。

### 评估用例的设计原则

当前先确定评估方向，不要求在实现前完成评测集。等最小端到端记忆链路明确后，再把评估方向落实为样本。样本应覆盖“输入信息 → 形成记忆 → 后续使用”的过程，而不是孤立的一问一答；每个样本写清输入、期望记忆、后续任务和判断依据。首轮用少量不同类型的样本覆盖主要能力，不照搬 S1–S14 做成 14 项独立功能。

| 任务类型 | 要观察的记忆能力 | 后续任务可以检查什么 |
|---|---|---|
| 个性化 | 能否记住用户明确表达、会影响未来交互的偏好，并在重复表达时避免无谓堆叠 | 后续回答是否按偏好调整，且没有把偏好扩展成用户没说过的要求 |
| 持续任务/项目 | 能否保留对后续工作有用的目标、约束、已作决定和进展 | agent 能否接着已有上下文工作，避免重复询问或违反已知约束 |
| 信息补充、变化和更正 | 能否区分补充、状态变化和明确纠正，保留仍有价值的旧信息及来源 | 后续任务是否使用适用的信息，不把已明确更正的内容当真，也不把不同情境硬合并 |
| 来源与证据 | 能否保留是谁说的、来自哪里以及可用的时间依据 | 需要依据时，agent 是否能正确引用来源，并区分用户陈述、assistant 建议和工具观察 |
| 无关或无依据内容 | 能否避免把闲聊、猜测或不相关材料写成可靠长期记忆 | 后续回答是否避免被无关旧内容干扰；没有足够依据时是否不编造 |

这些是当前的覆盖方向，不是现在必须全部落成的测试用例，也不限定唯一业务问题。位置变化/历史查询可以放入“信息补充、变化和更正”这一类，不能代表整套评估。

### 怎么判断记忆有没有效果

同一后续任务至少比较两种条件：不提供长期记忆；提供系统从前序输入实际形成并召回的记忆。对照时保持任务和回答模型设置一致。检查三个层面：

1. **记得是否正确**：保留了哪些信息，是否有依据，来源角色和时间是否准确，有没有漏掉重要内容或添出输入没有的事实。
2. **整理和召回是否合适**：重复是否堆叠，补充/变化/更正是否处理妥当；后续任务召回的是否是相关记忆，有没有被无关或过时内容带偏。
3. **是否帮助完成任务**：使用记忆后，任务结果是否更贴合用户已给出的偏好、约束和上下文；是否减少重复沟通；是否引入记忆导致的错误。

初期按这些标准逐例检查并记录失败，不以单个样本的分数推断总体效果。最小链路形成后再补齐并运行样本；有了失败证据后再扩大样本、重复运行并比较方案。

## 阶段 C：评估记忆是否改善后续任务

要回答“记忆整体有没有帮助”，还需选一组有代表性的后续任务，对比不使用记忆和使用记忆时 agent 的表现。任务可以涵盖按用户偏好调整回答、延续项目上下文、利用用户提供的约束、查询来源或过往状态等。重点检查任务完成质量、是否用了正确记忆、是否引入错误记忆，而不是只比回答文字是否相同。

小样本只能发现明显设计问题。要比较稳定性或准确率，之后再按失败类型增加不同表达和上下文，固定模型与参数并重复运行；当前阶段不把一个小原型包装成普遍性能结论。

### 原观察暴露的问题

修正前六组主跑共 22 次写入、23 次回答；另对 D/E/F 重复了 9 次写入、7 次回答。合计 31 次写入中有一次被替代目标校验拒绝，30 次回答调用完成。完成调用不代表答案正确。主要失败为：

1. 无价值的咖啡闲聊被保存；不变的 MySQL 加上未确定 ClickHouse 建议被误判为替代，而不是补充。
2. manager 既 patch 旧对象又新增表达同一结果的对象；写回未按最终 UPDATE 结果去重，还可能在替代后执行普通 patch，覆盖本应保留的旧正文。
3. 更正“40 是笔误，实际 14，并非裁员”丢失了纠错限定；回答错误地把它解释为真实人数变化。
4. staging 连通性检查被后续用户确认覆盖；未知截图被澄清后只剩最终环境，丢掉此前未知的背景。
5. 来源和日期字段可以形式合法但语义错误；回答也可能增加输入没有提供的要求、原因或历史时间边界。

### 本轮代码修正

**尽量复用上游整理机制。** 第一轮即提供 LangMem 的 `Done` 工具，因为原型只执行 `max_steps=1`，而上游默认第二轮才加入无变更出口。按本轮 `new_source_ids` 构造调用专属 schema；被新增/patch 的对象未引用本轮来源时，交给 Trustcall 原有校验修复流程。结构化工具调用、JSON Patch 应用、无变更旧对象回带仍使用上游实现，没有另写一套整理模型。

**写回先规划，再执行。** 同 ID UPDATE 与正文/事实时间完全相同的普通 ADD 合并为一个 UPDATE；明确替代仍 ADD 新 ID。替代和普通 patch 同时出现时，保留旧正文与来源；不同内容的竞争输出拒绝，不静默丢弃。冗余历史替代目标只有在本次候选可见链的当前终点也被显式请求时才省去；不是自动猜测目标。旧记录作为只读上下文保留，普通召回仍能返回它。

**收紧提示与工具说明。** 明确非矛盾补充、真实变化和明确更正的工具选择，保留纠错、计划、角色、未知/确认等限定；独立事实分开提取，闲聊不写。回答提示要求区分纠正与真实变化，按证据使用时间，不扩张偏好或补造原因。这些提示仍不能保证模型遵守。

具体实现和行为边界见 [v1 17.8](agent_long_term_memory_v1_design.md#178-多类型失败修正与当前交接状态2026-10-09)。没有新增持久字段、语义分类器、图数据库或检索融合，也没有引入普通整理删除。

### 结论与剩余修正重点

本轮解决了可以确定性检查的 UPDATE/ADD 协调、无变更出口、遗漏本轮来源的上游修复和替代后覆盖旧记录等问题，并观察到补充、纠正、闲聊跳过和工具结果使用的改善。随后提升“明确历史回填必须 ADD”的规则并复跑完整六组样本。

E 的旧候选确实被检索到，manager 也拿到了原消息和“环境未知”的正文；澄清后更新为“来自 staging”对当前配置问答是合理的，但系统仍不能回答“10 月 3 日当时为什么不能采用它”这类知识过程问题。保存的消息时间和来源 ID 不能单独重建被更新前的正文；这一限制不能归因于检索没有命中，也不能只加时间过滤解决。Mem0 的操作 history 可能保留旧文本，但当前回答链路没有读取它，而且它没有完整来源/事实时间 metadata 快照，不能宣传成已解决来源追溯。

历史回填规则已在完整六组复跑中生效：Atlas 的 2025 年 MySQL 历史被单独新增，2026 年 PostgreSQL 当前状态没有被再次 UPDATE；23 个回答调用均完成，且该问题的 2025 年 8 月回答没有再补出 SQLite 的无依据时间顺序。普通补充仍保持 UPDATE，不能因为一次历史回填失败就把所有信息改成 ADD。时间精度和回答中无依据的解释仍需继续观察；现阶段不宣称完整长期记忆质量达标，不以单个历史问题代替整体记忆效果评估。

- 两种同一偏好补充均使用 UPDATE，并合并新增细节和两条用户来源。

## 来源、时间和知识过程定向观察（2026-10-10）

随后用 4 组风险样本进行了 6 次写入、9 次回答，并将时间样本在回答参考时间晚于消息时间的条件下再跑 2 次写入、2 次回答；没有 API、写入或回答异常。

- **来源角色：** assistant 的“每天备份”建议被单独保存，并标明尚未确认；工具观察也被回答为工具结果而不是用户确认。但一次工具记忆仍把 user、tool、assistant 三个来源 ID 放在同一条记录上，来源还不能精确到每个句子。
- **事实日期：** 原文明确写“2026 年 10 月 1 日起”的迁移记录正确写入 `valid_from=2026-10-01`。
- **无明确事实日期：** 原文只有“现在我在上海”时，模型仍写入了 `valid_from=2026-10-11`，实际是从 `observed_at` 推出来的。这个边界已记录，但按当前 v1 范围暂不处理；普通查询仍以消息观察时间和正文语义回答。
- **知识过程：** 后来把环境未知澄清为 staging 后，正文保留了“此前未知”的限定，但回答“10 月 3 日当时知道什么”时仍使用了 10 月 7 日才得到的 staging 结论。这个问题属于审计型“当时系统知道什么”查询，不是当前普通长期记忆目标，v1 暂不提供点时知识快照。

因此不再为这两个边界继续扩大样本或增加 v1 机制。原始观察仍保留作限制证据，见[风险定向观察记录](../examples/agent_memory_v1/tests/observations/20261010_risk_observation.json)和[风险 fixture](../examples/agent_memory_v1/tests/fixtures/memory_risks.json)。DB-GPT 实际 agent 链路的默认关闭桥接已经完成；下一步转入正式记忆评测，而不是再次进行链路接入。

## LongMemEval-S 正式评测接线（2026-10-12）

已开始把正式评测接到现有原型。适配器位于
`examples/agent_memory_v1/evaluation/longmemeval.py`，目前只负责 benchmark 数据解析、按 session 顺序回放、每题独立 scope/本地 Qdrant、问题检索、回答记录和官方预测 JSONL 输出；没有改动 `MemoryService` 的提取、写回或召回策略。

当前接线约定如下：

- 每道题使用独立 `user` scope；问题、gold answer、`answer_session_ids` 和 `has_answer` 不进入记忆写入。
- `haystack_sessions` 按文件顺序回放，每个 session 作为一次写入单元；session 内保留 user/assistant 角色，session 日期作为来源消息的观察时间。
- 问题的 `question_date` 作为回答侧 `reference_time`；检索候选连同 source refs、事实时间、记录时间和替代关系写入详细 `records.jsonl`。
- `predictions.jsonl` 每题都保留一行；运行失败的题目写空答案并计入失败，不能通过跳过失败题抬高分数。
- 先用 `--dry-run` 做字段/顺序/隔离检查，再做小样本 API pilot。2026-10-12 已对 11 道去重诊断题运行 DashScope 自定义 judge：9/11；按题型平均 80%；弃答 1/1。该样本经过挑选，不能代表完整数据集准确率，也不是与论文同口径的官方 GPT-4o 分数。

执行契约和清单见 [LongMemEval-S 接线计划](../examples/agent_memory_v1/evaluation/PLAN.md) 与 [执行清单](../examples/agent_memory_v1/evaluation/CHECKLIST.md)。LongMemEval 上游 QA evaluator 的任务类型判分标准可供参考；DashScope/Qwen 替代评委使用适配提示词和接口，结果必须单独标注为自定义 judge，不应称作论文同口径官方分数。逐题结果和指标见 `data/longmemeval/runs/20261012_qwen3_8_max_judge11/`。
