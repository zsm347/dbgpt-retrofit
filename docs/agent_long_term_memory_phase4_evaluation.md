# Agent 长期记忆：阶段 4 基座与复用路线评估

> 状态：源码审查、小规模组件探针和第一轮真实组合链路观察已完成；写入约定、架构方向和召回原则已讨论确认；尚无完整链路质量评测。  
> 日期：2026-09-29；实施进度同步：2026-10-09。  
> 目标需求：[v1 设计草案](agent_long_term_memory_v1_design.md)；场景基线：[S1–S14 场景矩阵](agent_long_term_memory_scenarios.md)。  
> 比较基线：Mem0 OSS `2.2.1`、LangMem `0.0.30`、`graphiti-core 0.30.2`，与已完成的固定版本源码审查一致。

## 1. 先说评估结论

**2026-10-08 的取舍是复用优先：实施起点采用 Mem0 存取/检索 + LangMem 无状态 manager，应用补薄适配层。** 复用 LangMem 结构化提取/patch、参考其 Store Manager 的 ID/内容比较；来源/时间、变化和纠正的旧记录保留以及用户遗忘由封装补齐。Graphiti 继续作来源和时态设计参考。2026-10-09 第一批共同依赖、导入和无外部模型写回接线已检查，第二批最小替代写回、普通召回与遗忘也已实现并通过 fake/stub 检查；随后完成了第一轮真实模型/embedding 组合观察，但尚无整体质量评测。真实运行暴露的时间来源和新旧排序限制见[原型评估](agent_long_term_memory_prototype_eval.md)。下文保留原路线比较的证据，当前编码以 [v1 实施说明 16、17](agent_long_term_memory_v1_design.md)为准。

原因是 v1 的关键要求是记住对未来有用且有依据的信息，保留来源角色与可用时间，并在多类后续任务中正确使用；状态历史只是其中一项能力，历史查询只是一个用例。这三套默认实现都不能原样满足：Mem0 `2.2.1` 的自动写入是 add-only；LangMem 可以自定义抽取和更新，但 Store Manager 会覆盖当前文档、不会自动保留事实版本；Graphiti 的时间关系和 episode 来源最完整，但把全部首期记忆放进图数据库会引入与当前目标不成比例的模型和运行负担。

这是基于目标数据语义、固定版本源码和有限组件探针得出的**原型架构建议**，不是代码量、准确率或任务效果实测。LangMem 可以按自定义 schema 提出候选，但探针也观察到重复/补充输入可能同时产生旧条目更新和新概括，写回前需要校验。Mem0 有更完整的自动 `add/search` 路径；位置变化探针的原话含“现在”，输出把它概括为观察日期附近的变化。这个近似日期有提示词中的观察日期作为参照，可用于表达“消息当时报告的状态”，但不证明事实在那一天精确发生。两者都不能直接替代我们的记忆契约和历史策略。

若组合依赖或适配出现实证问题，先寻找更少改动的现成组件替代，再判断是否需要自行实现。Graphiti 的时态图代码只有在关系查询确实需要图数据库时才纳入实现路线。

## 2. 比较依据与判断尺度

v1 需要的核心能力是：可信范围隔离；记忆有来源；来源角色明确；区分来源消息时间、系统记录时间和有依据的事实时间；能保留状态变化和明确更正；召回结果能带来源/时间证据给回答模型。普通 Top-k 不承诺完整历史。详细边界见 v1 草案。

本文使用以下等级，避免把“仓库里可以定制”误写成“开箱即有”：

| 等级 | 含义 |
|---|---|
| 现成 | 固定版本默认路径已提供，适配工作有限。 |
| 部分 | 有接口或组件可复用，但关键约束仍要由我们补上。 |
| 自建 | 需由项目自己的策略、数据层或查询逻辑实现。 |

改造量用低/中/高描述达到 v1 语义的相对工程范围，不是人日估算，也不是运行表现。它不包含 DB-GPT agent 链路接入；该工作仍按计划后置。

### 组件探针提供了什么证据

2026-09-29 在隔离环境中对 `langmem==0.0.30` 和 `mem0ai==2.2.1` 做了少量合成输入探针。它们与源码审查互补，用来确认调用边界和实际输出，不构成效果排名：[探针输入、观察和限制](agent_long_term_memory_prototype_eval.md)。

| 组件路径 | 探针观察 | 对路线的影响 |
|---|---|---|
| LangMem 无状态 manager | 调用方提供旧候选；重复/补充输入有时既返回旧条目更新，又产生新概括条目。 | 复用结构化提取，写回比较 ID/内容并校验来源；重复控制需运行观察，不因此预设六种关系枚举或新的冲突分类器。 |
| Mem0 `add()` | 它自行检索旧候选；重复输入本次没有新增，补充和状态变化会另存新条目。位置变化输入含“现在”，输出日期落在观察日期附近。 | 可作为完整自动写入/搜索对照；应把观察日期理解为消息时间参照，不误当成精确的事实发生时间；不能把 ADD-only 等同于可靠历史管理。 |
| Graphiti | 本轮没有安装或运行组件；结论来自固定版本源码审查。 | 只把 episode 来源关联和事实有效时间分离作为设计参考；图数据库运行成本暂不进入 v1 原型。 |

这些观察来自少数调用、一个模型配置和合成数据。若两条路径检索到的旧候选不同，不能据此比较提取器准确率；也没有测试整套记忆系统是否提高 agent 任务完成质量。

## 3. 路线逐项比较

### A. 直接以 Mem0 OSS 为基座

**现成可复用：** 有记忆条目、scope 查询、自动抽取、写入候选搜索和普通搜索 API；普通 `search()` 可组合语义候选、BM25 词项和实体分数，并可选 rerank。Python SDK 对“记忆读写”开箱体验最直接。小探针里 `add()` 能自行找到旧候选，重复输入未新增；补充和状态变化则新建条目。

**必须补齐：** 当前自动 `add(infer=True)` 只新增候选，不能据此解决同一属性更新或冲突；默认记忆不是带原始消息 ID/角色/事实有效区间的证据记录。小探针曾生成输入未提供的日期，因此要加时间来源校验。要满足 v1，仍需另加来源引用、时间字段约定、历史保留，以及新旧关系的写入策略和回答上下文格式。

**依赖与许可：** 审查版本 `mem0ai==2.2.1` 为 Apache-2.0；核心依赖包括 Qdrant client、Pydantic、OpenAI SDK、SQLAlchemy 等，许多其他向量库和模型接入以 extras 提供。底层向量库、数据库和模型服务仍需单独配置/核查。[固定版本 pyproject](https://github.com/mem0ai/mem0/blob/94c3fe9f238f3dbf29c9ce98643bd71eb13077cd/pyproject.toml)、[固定版本写入实现](https://github.com/mem0ai/mem0/blob/94c3fe9f238f3dbf29c9ce98643bd71eb13077cd/mem0/memory/main.py)

**相对改造量：** 做一个可运行的 demo 是低；达到本项目的来源、时间与历史语义是中到高。复用面主要在记忆 API、抽取/搜索管线和存储适配；核心新旧决策不能直接复用当前默认策略。若深度 fork，未来升级时需持续解决自定义行为与上游实现的差异。

### B. 以 LangMem 为基座

**现成可复用：** 结构化 schema 和无状态 manager 可抽取/整理候选；调用方可以先搜索旧记忆，再把有限的相关候选作为 `existing` 传给 manager；抽取逻辑与存储接口分开，适合作为独立部件候选。小探针确认它能提出更新，但也观察到重复/补充输入可能多产一条概括记忆。

**必须补齐：** 默认 schema 不带完整来源和事实时间契约；检索依赖 BaseStore 配置且候选数量有限；Manager 的 patch 更新不等于保存旧版本。若直接用 Store Manager 做唯一写入层，还要补版本留存、来源证据、新旧关系、范围校验和冲突不裁决策略。若只调用无状态 manager 输出候选，则这些决策和写回都由我们负责。

**依赖与许可：** 审查版本 `langmem==0.0.30` 为 MIT；它的声明依赖包括 LangChain、LangGraph、Trustcall、LangSmith 及 OpenAI/Anthropic 集成等。持久化 Store 不是 LangMem 自带数据库，需另选 BaseStore 实现并配置索引。若 DB-GPT 主体不使用这套生态，运行依赖和版本兼容要单独核查。[固定版本 pyproject](https://github.com/langchain-ai/langmem/blob/56d85939d80bb731bd5e237567148d817d7bfd16/pyproject.toml)、[固定版本提取与 Store Manager](https://github.com/langchain-ai/langmem/blob/56d85939d80bb731bd5e237567148d817d7bfd16/src/langmem/knowledge/extraction.py)

**相对改造量：** 基础提取 demo 是低到中；满足 v1 的历史/来源语义是中到高。推荐只把无状态 manager 作为候选提取器，并自建 version-aware 写回，不依赖它的 Store Manager 持久化语义。若直接采用 Store Manager，则需要额外解决覆盖旧值、来源留存和历史查询。

### C. 以 Graphiti Core 为基座

**现成可复用：** episode 来源、实体和事实关系、事实有效/失效时间、混合事实搜索，以及冲突后保留旧关系的路径，三者里时间关系模型最完整。它适合关系密集、需要跨实体/事件查询、且时态图是核心需求的系统。

**必须补齐：** 角色可信度和“用户陈述/assistant 建议/工具观察/用户确认”仍要另建规则；默认模型没有 v1 所需的未决冲突状态；普通 `search()` 默认不保证只返回当前有效事实；单项偏好和简单用户属性也不天然需要转成图边。它的候选集和时间推断仍有边界，不能把图结构当成自动正确的冲突裁决。

**依赖与许可：** 审查版本 `graphiti-core==0.30.2` 为 Apache-2.0，Python 主依赖含 Neo4j driver、Pydantic、OpenAI SDK 等；另需运行一个兼容的图数据库。FalkorDB、Neptune 等后端通过可选 extras 接入，不同后端的检索能力和外部服务条款另算。[固定版本 pyproject](https://github.com/getzep/graphiti/blob/eaa4128681bc53487138a4bbc22d58336ebe70d2/pyproject.toml)、[固定版本 episode 写入路径](https://github.com/getzep/graphiti/blob/eaa4128681bc53487138a4bbc22d58336ebe70d2/graphiti_core/graphiti.py)

**相对改造量：** 仅验证用例就需要图数据库和多路模型/向量流程；达到 v1 还要补角色证据、冲突边界和回答侧时间过滤。相对为高。若未来明确要求复杂实体关系、事件关联和时间段遍历，它的复用价值会明显上升；在当前记忆范围内，图数据库是额外运行面。

### D. 自己实现记忆核心，复用存储/检索适配器

**现成可复用：** 可复用选定的 LLM/embedding 客户端、向量或关键词搜索后端；也可在原型中复用 LangMem 的无状态结构化提取器，或把 Mem0 搜索作为对照组件。记忆对象、来源、时间和新旧变化由我们定义，不继承某个库的写回语义。

**必须自建：** 记忆输入 envelope、抽取 prompt/schema、写入候选构造、重复/补充/变化/纠正的处理、可追溯保存、幂等和失败边界，以及把证据组织给回答模型的接口。存储适配器需要实现严格 scope 过滤；后端不支持某些精确查询时要明确报告能力边界。

**依赖与许可：** 没有新增“长期记忆框架”的主许可证；选择哪个存储、模型客户端或提取组件，就需分别核查各自许可证和依赖。整体依赖可以更窄，但策略、兼容和维护责任全部由项目承担。

**相对改造量：** 一个最小纵向原型是中；持续维护成本取决于是否坚持窄范围。它不一定比包一层 Mem0/LangMem 的首次代码量更少，但能减少为绕过框架默认 schema/写回历史而做的适配。关键是限定 v1：一类消息输入、基本记忆条目、来源引用、可选事实时间、简单候选检索和可追溯新旧关系；不先建图或复杂状态机。

### 发布节奏观察

本评估固定的是源码审查过的包版本。按 2026-09-29 可见的 PyPI 发布信息，Mem0 `2.2.1` 发布于 2026-09-25，Graphiti `0.30.2` 发布于 2026-09-08，LangMem `0.0.30` 发布于 2025-10-27。LangMem 的包发布间隔较长，是依赖更新和兼容性核查项；**单看 PyPI 发布间隔不能据此断言其源码仓库停止维护**。选型前需再核对实际要用的 commit 与锁定依赖。

## 4. 对照表

| 评估项 | Mem0 基座 | LangMem 基座 | Graphiti 基座 | 自研核心 + 复用搜索 |
|---|---|---|---|---|
| 用户事实/偏好抽取 | 现成 | 现成且 schema 灵活 | 可抽取，但数据模型偏关系图 | 自建，可组合提取器 |
| 来源引用与角色区分 | 部分，需补消息级证据 | 部分，schema 可扩但要补 | episode 引用现成；信任角色需补 | 按目标契约自建 |
| 时间和事实历史 | 弱，需补 | 弱，需补 | 强于其他路线，但不能自动覆盖所有时态查询 | 按首期最小要求自建 |
| 新旧关系处理 | 当前路径 add-only；需补业务策略 | patch/CRUD 有，历史保留要补 | 有条件地使旧事实失效并保留图边 | 自建且可直接匹配需求 |
| 普通检索 | 直接，有混合排序路径 | 取决 BaseStore | 图/全文/向量能力丰富，运行成本较高 | 复用所选后端，查询策略自建 |
| 外部存储负担 | 需要选向量/元数据后端 | 必须选 BaseStore；LangMem 不提供持久库 | 必须运行图数据库 | 需要选后端，可先用现有基础设施但本阶段不绑定 DB-GPT |
| 依赖/生态耦合 | Mem0 API 与配置约定 | LangChain/LangGraph/Trustcall 生态 | Graphiti schema 与 graph driver | 最低框架耦合，最高自有维护责任 |
| v1 相对实现成本 | 中到高 | 中到高 | 高 | 中 |
| 主要适用条件 | 希望最快获得现成 add/search，且接受自定义历史层 | 已在使用 LangGraph，或希望复用其 manager/store 抽象 | 记忆主体是跨实体关系和时间图查询 | 需要按自有语义控制历史、来源、时间，且希望避免框架数据模型锁定 |

所有“成本”均为相对工程估计，不是统一团队、数据集和基础设施上的实测值。三个包自身的宽松许可证并不自动覆盖它们的全部可选依赖、数据库服务或模型服务；确定部署组合前仍要核查完整软件物料清单和对应条款。

## 5. 推荐路线与可复用边界

### 当前实施起点（2026-10-08）

**优先组合已有组件：Mem0 存取/检索 + LangMem `create_memory_manager` + 薄适配层。** Mem0 公开 `search()` 提供候选；manager 根据新消息和候选完成提取/整理；写回参考 LangMem Store Manager 的 ID 与内容比较，调用 Mem0 `add(infer=False)` 或 `update()`，避免二次提取。来源 ID/角色/时间由输入封装明确提供，写回校验引用和范围。

底层只保留跳过、新增、更新三种普通整理动作；重复默认不新增，非矛盾补充可更新，变化/纠正新增并保留旧记录；用户要求忘记走单独删除。不要求六值 `relation`，变化与纠正的语义通过内容和必要的旧 ID 引用保留。Mem0 的 history 可作操作追踪，不能替代普通可召回的旧记录。

近期上下文从聊天记录提供并标明输入分区；仅调用 Mem0 `search()` 或 `add(infer=False)` 不会获得自动 add 的近期消息和实体关联流程。LangMem 固定模板中的通用更新指令需要小范围适配。组合依赖、metadata 存取及具体后端在实施中确认，当前未声称组合已可运行或效果已验证。

### 从三个项目中借用什么

- **Mem0：** 优先直接复用存取/检索及其后端适配；提示词和近期上下文按源码参考，不照搬 ADD-only 操作或提取数量要求。
- **LangMem：** 复用无状态 manager/Trustcall 的结构化提取和 patch；参考 Store Manager 的写回比较，适配到 Mem0 API。
- **Graphiti：** 参考来源 episode 关联和“事实时间与系统记录时间分开”的原则；只有真实需求需要实体图关系时，再引入 Graphiti 或单独图索引。

## 6. 当前尚待决定的设计

1. **已完成：组件源码审查与行为探针。**它们帮助判断可复用边界，不证明哪套实现的记忆效果最好。
2. **已讨论确认：召回先按范围找相关记忆，不因记录较旧就预先过滤；将内容、来源和时间交给 agent 结合任务使用。**首版不为每种问法建专门规则，也不全局偏向最新记录。
3. **已完成第一轮真实模型与 embedding 观察。** 重复、补充、状态变化、替代写回和普通召回均跑通；无明确事实日期时的时间字段污染、旧记录排序问题已记录。
4. **下一步：针对真实运行暴露的问题做窄范围修正/观察。** 先决定最小事实时间来源校验，再用多类任务观察回答模型是否正确利用 `superseded_by`、来源和时间；不重做第一批环境或组件探针。
5. **记忆效果评估留到上述修正后的链路稳定后。** 届时再用多类后续任务比较有无记忆的表现，不把某一个历史问答例子当作整体标准。

输入、schema、完整 instructions 草案、来源目录与 ID 映射、Mem0 metadata 和公开 API 调用、写回比较、召回上下文、失败边界及配置起点，现已集中记录在 [v1 设计与实施说明](agent_long_term_memory_v1_design.md)的“实施说明”部分。原路线比较提供取舍依据；具体编码以该文件为准，不重复设计一套不同字段。

同一输入与同一模型配置有助于比较，但如果两条路线实际拿到的旧记忆候选不同，结果只能代表两条端到端接入路径，不能单独归因于提取器。每一步应记录输入、候选、返回值、写入结果和问答召回证据；不按最终回答文字或单一总分选路线。

具体组件观察和效果评估范围见[原型评估设计](agent_long_term_memory_prototype_eval.md)。当前两批最小代码链路已实现，并已用真实模型/embedding 做过第一轮小规模组合观察；尚未测准确率、任务表现、延迟或端到端改造工时，整体记忆效果和路线成本仍未被实测证明。

## 7. 阶段 4 小结

- 当前没有一个项目可以原样提供目标 v1 的完整语义。
- Mem0 的优势是可快速开始写入和搜索，但当前默认写入算法不提供状态冲突管理。
- LangMem 的优势是 manager/schema/store 可组合；它更适合做可替换的提取组件，不自动提供可追溯的历史版本。
- Graphiti 的优势是时态关系图和 episode 来源；代价是图数据库和超出 v1 的数据模型。
- **当前工作原则是开源复用优先，实施起点是 Mem0 存取/检索 + LangMem manager + 薄适配层。** 需要补的部分限制在已确认需求的缺口，不预设大规模自研核心。
- Graphiti 作为时态来源设计参考；共同依赖、无外部模型接线和第一轮真实组合调用已检查，最终部署后端未定。
- 探针和真实运行都只提供适配风险线索，没有证明 LangMem 提取效果最好。时间提示的第一轮修正和回答侧 `reference_time` 薄接线已完成；下一步是用多类任务开展完整链路记忆效果评估，再决定是否需要额外的时间校验或查询过滤。
